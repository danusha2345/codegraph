## Замечания, подтверждённые отрицательными controls

### PHP: регистр и неоднозначная область импорта

Исходный #2257 не разрешал `new field\FirstName()` после `use App\Fields as Field;`.
При повторном alias `Field` в двух namespace одного файла он выбирал первый
импорт для обоих вызовов: второй `new Field\FirstName()` получал неверное ребро.

Alias теперь сравнивается без учёта регистра. Если файловая таблица содержит
разные назначения одинакового alias, resolver оставляет ссылку неизвестной.
Это предотвращает ложные рёбра; полная таблица импортов по namespace scope
ещё не реализована. Controls также проверяют отсутствие подстановки местного
одноимённого класса вместо внешнего namespace.

Правило перевода первого сегмента и раздельные таблицы импортов описаны в
[руководстве PHP](https://www.php.net/manual/en/language.namespaces.rules.php).

### Windows: отрицательные spread и повторные call sites

Новый guard из #2255 пропускал `{ windowsHide: true, ...{ windowsHide: false } }`
и неизвестный spread. Кроме того, общий набор посещённых AST-узлов делал второй
call site с тем же безопасным initializer ложным нарушением. Форма
`spawn(command, optionsVariable)` тоже не распознавалась.

Guard теперь различает отсутствующее свойство, true, false и неизвестное
значение, учитывает порядок spread и отслеживает циклы отдельно на каждом пути.
Новые controls воспроизводят все перечисленные случаи.

При запуске на нашей интеграции guard дополнительно обнаружил пропущенный
`windowsHide` у `spawn` в `src/hdl/semantic-runner.ts`; опция добавлена.
Реальный Windows-прогон не выполнен: доступная среда — Linux.

### Viewer: один обработчик не должен вытеснять остальные маршруты

В исходном #2264 выборка `limit * 4 + 1` строк выполнялась до устранения дублей.
При `limit=3` первый inline-handler с 24 вызовами занимал всю выборку, и viewer
возвращал только один маршрут вместо трёх.

Для viewer лимит теперь применяется к уникальным маршрутам в SQL, а сведения
об обработчике берутся из общего `routeRoots`. Обычная семантика публичного
`getRoutingManifest(limit)` сохранена; режим уникальных маршрутов включается
дополнительным аргументом. Отрицательный control проверяет полный список из
трёх маршрутов после насыщенного обработчика.

Дополнительный control сохраняет прежнее обнаружение приложения с одним
inline-маршрутом и несколькими вызовами в его теле. Режим уникальных маршрутов
использует ограниченную legacy-пробу для прежнего порога уверенности.

Дедупликация членов Astro-компонента и схлопывание пустых веток Steps из #2264
сохранены. Controls с 80 пустыми проверками проходят.
